  1. Schemas

  - User: name and email are required Strings, and email is unique. pendingTasks
    is [String] defaulting to []. dateCreated uses timestamps: { createdAt: 
    'dateCreated', updatedAt: false }, which is immutable and ignores client
    input.
  - Task: name and deadline are required. description defaults to "". completed
    defaults to false. assignedUser defaults to "". assignedUserName defaults to
    "unassigned". dateCreated is handled the same way as on User.
  - Use strict type checks and avoid Mongoose coercion, so that name: 123 or
    completed: "yes" returns 400.
  - Don't rely on the unique index alone for the duplicate-email check. Do an
    explicit lookup that excludes the current user, so a user keeping their own
    email is fine. Keep the index as a backstop and map code 11000 to 400.

  2. Query parsing (utils/query.js)

  - JSON.parse the where, sort, and select parameters. Invalid JSON returns 400.
  - Parse skip and limit as non-negative integers. Anything else returns 400.
  - Apply them with Mongoose: Model.find(where).sort().select().skip().limit().
  - count=true calls Model.countDocuments(where), so it respects where and
    ignores the other parameters.
  - Default limit is 100 for tasks and unlimited for users.
  - A where with a bad _id cast or an unsafe operator returns 400. I'll allow
    normal operators like $in and reject $where.
  - GET /:id returns 404 for a malformed or missing id and honors only select.
    It ignores all other parameters.

  3. Response and error conventions

  - Every response is { message, data }.
  - Status codes: 200 on GET, PUT, and DELETE (the README requires a 204
    somewhere; I'll decide where below), 201 on POST, 400, 404, and 500.
  - 500 responses return a generic message and never include Mongoose text. I'll
    log the real error on the server.

  4. Validation order for POST and PUT

  Per the README: URL id (404), then field format and values (400), then whether
  referenced users or tasks exist (404), then state conflicts such as a
  completed task in pendingTasks (400). The FAQ table also puts the
  duplicate-email check (400) before the existence check (404). Nothing may be
  written until all checks pass.

  5. Two-way reference logic

  I'll put this in one shared helper so the routes stay thin.

  - PUT /users/:id
    - Load the user. If it's missing, return 404.
    - Validate name, email, and pendingTasks: it must be an array of valid
      ObjectId strings, with duplicates removed.
    - Check the email isn't used by another user.
    - Load every task in new. A missing one returns 404, and a completed one
      returns 400.
    - Then apply the updates:
      - For tasks in old but not in new, set assignedUser to "" and
        assignedUserName to "unassigned".
      - For tasks in new that belong to another user, $pull them from that
        user's pendingTasks.
      - Assign all tasks in new to this user.
      - If the name changed, update assignedUserName on all of the user's tasks,
        completed ones included.
      - Save the user. dateCreated is preserved.
  - POST /users: the same as PUT, with a new _id and old = [].
  - PUT /tasks/:id
    - Return 404 if the task is missing. Return 400 for a missing name or
      deadline, a malformed assignedUser, or an assignedUserName that doesn't
      match the user.
    - Return 404 if a valid assignedUser doesn't exist.
    - Fill in assignedUserName if it's omitted. assignedUser: "" sets the name
      to "unassigned".
    - If the previous user differs, $pull the task from the previous user's
      pendingTasks.
    - If assigned and not completed, $addToSet the task onto the new user's
      pendingTasks. If completed, $pull it.
    - Replace the task and preserve dateCreated.
  - POST /tasks: the same as PUT, minus the previous-user handling.
  - DELETE /tasks/:id: $pull the task from its assigned user's pendingTasks,
    then delete it.
  - DELETE /users/:id: unassign all of that user's tasks via updateMany on
    assignedUser, then delete the user.

  Atomicity: Atlas free tier is a replica set, so I could use
  mongoose.startSession() with withTransaction to guarantee "nothing changes on
  failure". The alternative is to do all validation up front and then write in a
  safe order. I'd go with validate-first, which is simpler and less brittle.
  I'd add a transaction only if it turns out to be cheap.

  What changed
  - Every mutating handler is one transaction: POST, PUT and DELETE on users and
    on tasks. Each request commits all of its changes together or none of them.
  - Reads happen inside the transaction too: The document being updated, the
    email check, the task lookup and the assigned-user lookup all use the
    session. If two requests conflict, MongoDB aborts one and the driver re-runs
    it from fresh reads.
  - Parallel queries are gone from the write paths: I had added Promise.all
    calls in the cleanup, but running queries in parallel on one transaction
    session isn't supported, so those are sequential again. I kept the
    one-call-per-owner grouping for moved tasks, since that's a plain loop.
  - GET requests are not in a transaction.
